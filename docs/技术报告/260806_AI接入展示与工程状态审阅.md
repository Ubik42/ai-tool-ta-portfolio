# AI 接入展示与工程状态审阅

时间：2026-08-06 10:50  
当前稳定基线：R75 / `dcc-first-package@1.72.0` / Presenter Pack 73 evidence / 63 route。

## 结论

当前工程已经是一个很强的 DCC / 引擎工具 TA 证据工程，但“AI 接入”在展示上还偏弱。强项是确定性管线：DCC facts、规则门禁、owner action、受控写入、rollback、Presenter Pack。弱项是 reviewer 第一眼看到的是自动化和 runtime proof，不会立刻感知 AI 在工具链里承担了什么角色。

最合适的讲法不是“AI 自动做资产”，而是：

> 这是一个 DCC / 引擎内的 AI Tool TA Workbench。确定性代码负责采集、校验、执行和回滚；AI 负责读懂复杂证据、聚类问题、生成 owner handoff、解释风险和建议下一步。AI 不越权改资产，所有 mutation 都经过 deterministic gate 和 receipt。

## 当前 AI 展示弱点

已有基础：

- `PRODUCT.md` 明确写了 AI subordinate to production truth。
- 前端模块数据有 `aiRole`。
- Visual Review 有 review draft。
- Task Orchestrator 有 `buildAiHandoffDraft`，并明确 `AI boundary: draft handoff text from module reports only; deterministic module gates remain authoritative.`
- 多数 artifact 已经有 owner action、fix preview、write boundary，这些非常适合喂给 AI 做解释和分派。

不足：

- AI 不是 Presenter Pack 的一等证据，没有统一 `ai-review-packet@...`。
- DCC 面板里没有一个明确的“AI triage / AI handoff / AI recommendation”入口。
- 当前演示路线大多是 Run scripts / Export evidence，AI 角色被埋在描述里。
- 没有把 AI 输出和 deterministic evidence refs 绑定起来，reviewer 看不到“AI 是根据哪几条事实做出建议”。
- 没有展示 AI 输出的可编辑、可接受、可拒绝、可审计状态。

## 建议改造

下一步不要继续堆新 DCC 线，先补 AI 主线：

1. 新增 `AI Review Packet` 通用 schema  
   输入：任意模块 artifact、evaluation rows、ownerActions、write boundary。  
   输出：`summaryDraft`、`rootCauseClusters`、`ownerHandoffDrafts`、`safeNextActions`、`blockedReasons`、`evidenceRefs`、`aiBoundary`、`accepted/edited/rejected`。

2. 在 Maya AuroraView Host 里加 `AI Triage` 展示入口  
   让 reviewer 在 DCC 内看到：为什么 blocked、谁要处理、哪些能自动修、哪些必须 owner、AI 草稿引用了哪些 evidence rows。

3. 先覆盖三条最强业务线  
   - Socket / Gameplay Attach：AI 解释 attach 链路为什么 blocked / ready。
   - Control Rig：AI 解释 compile status、commandlet、fixture readiness。
   - Groom：AI 解释 Alembic / GroomAsset / BindingAsset 的业务闭环。

4. 讲法统一  
   每条 case 都按同一结构讲：真实业务问题 -> deterministic facts -> AI triage -> controlled action -> receipt proof。
