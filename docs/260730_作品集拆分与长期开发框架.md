# 260730 作品集拆分与长期开发框架

结论：作品集要拆成多个工具，但要放在同一个产品壳里。

最优结构不是“一个大而全工具”，也不是“十几个孤立 demo”，而是：

```text
AI Tool TA Portfolio
├── 统一入口：Production Toolbench
├── Tool 1：Asset Protocol Workbench
├── Tool 2：Cross-DCC Rule Matrix
├── Tool 3：Visual Review Studio
├── Tool 4：Texture Delivery Console
└── Tool 5：Task Orchestrator
```

每个工具独立可讲，组合起来又能形成一套真实 TA 生产平台。

## 为什么拆

作品集评审不会只看“会写前端”或“会接 AI”。真正有价值的是证明你理解业务工具的核心结构：

- 资产语义如何进入数据。
- 项目规范如何变成 schema、规则和自动修复。
- DCC 不确定状态如何被压平成确定性交付。
- 视觉评审如何固定视角、pass 和报告。
- 贴图、LOD、材质、任务系统如何串成生产链路。

这些能力放在一个工具里会失焦；拆成模块更容易讲清“一个真实业务秘诀”。

## 模块边界

### 1. Asset Protocol Workbench

方法来源：

- `maya_asset_tool_reference/asset_protocol_editor_reference`
- `og2_vehicle_light_tools`
- `maya_asset_tool_reference/lod_texture_bake_reference`
- `tangent_save`
- `save_vertex_normal_info`

展示重点：

- 资产协议不是表单，是资产状态机。
- 平台、LOD、collision、Nanite、streamable、screen size、cull distance、材质、贴图、asset platform 元数据统一进入资产协议。
- UV / vertex color / custom attr 可以承载业务语义。

首版功能：

- synthetic asset fixture。
- 协议字段编辑器。
- payload 编码预览。
- 风险提示：缺失字段、平台冲突、预算不一致。

### 2. Cross-DCC Rule Matrix

方法来源：

- `maya_publish_rule_reference`
- `maya_rule_adapter_reference`
- `blender_rule_adapter_reference`
- `max_rule_adapter_reference`
- `houdini_rule_adapter_reference`

展示重点：

- 同一业务规则和 DCC adapter 分离。
- collect / validate / fix / extract 是可复用协议。
- severity、fixability、selection action 要配置化。

首版功能：

- 规则 DSL。
- Maya / Blender / Max / Houdini adapter mock。
- 执行矩阵。
- AI 解释层：把规则失败转成 TA 可读诊断。

### 3. Visual Review Studio

方法来源：

- `maya_visual_review_reference/shelf/tools/visual_compare_reference`

展示重点：

- 视觉评审靠固定相机、固定材质 pass、固定命名和报告稳定性。
- red-blue overlay、white-blue material、solo variant、LOD/detail split 是可复用审查模式。

首版功能：

- baseline / variant fixture。
- 多相机多 pass review queue。
- 差异分数和失败原因。
- HTML report mock。

### 4. Texture Delivery Console

方法来源：

- `texture_to_engine_reference`
- `substance_delivery_reference`
- `photoshop_dds_reference`
- `spritesheet_reference`
- `substance_shader_reference`

展示重点：

- 贴图交付不是文件复制，是命名、通道、压缩、mipmap、预览、引擎同步。
- 长任务需要 worker、progress、log、取消和失败原因。

首版功能：

- 通道打包 preset。
- DDS / spritesheet / UE import mock。
- 队列状态和失败定位。
- AI 风险说明：哪些参数会导致平台问题。

### 5. Task Orchestrator

方法来源：

- `task_intake_reference`
- `task_manager_backend_reference`
- `asset_platform_sync_reference`
- `tool_shelf_reference`
- `tool_discovery_server_reference`

展示重点：

- 工具平台要能发现、注册、热更新、上报。
- 任务、资产、QC、review、publish 要有状态流。
- 外部平台 adapter 和本地工具执行边界要清楚。

首版功能：

- 任务流 Kanban。
- asset package 状态。
- 模块执行记录。
- publish readiness checklist。

## 复杂度分层

### 第一层：可运行壳

目标是让作品集像产品，而不是文档目录。

交付：

- `showcases/portfolio-site`
- 统一导航。
- 模块矩阵。
- 开发循环状态。
- 每个模块的 case card。

### 第二层：规则和 fixture

目标是把真实业务经验转成公开合成数据。

交付：

- `fixtures/assets`
- `fixtures/rules`
- `fixtures/reports`
- 每个模块至少 3 个正例、3 个反例。

### 第三层：确定性核心

目标是让 demo 不是假 UI。

交付：

- schema parser。
- validation engine。
- diff generator。
- report generator。
- deterministic mock executor。

### 第四层：AI 增强

目标是体现 AI Tool TA，而不是 AI 聊天玩具。

交付：

- 规则草案生成。
- 失败原因聚类。
- 修复建议解释。
- publish 风险总结。
- case study 自动摘要。

### 第五层：证据资产

目标是让作品集能被评审快速判断。

交付：

- screenshot。
- demo video。
- before / after data diff。
- generated report。
- case-study md。

## 长期循环节奏

每一轮只推进一个明确增量：

1. 选一个 Lightbox 方法点。
2. 抽象成公开业务场景。
3. 写 case card。
4. 准备 synthetic fixture。
5. 写确定性执行核心。
6. 接 UI 控件和状态。
7. 加 AI 解释或生成能力。
8. 生成证据：截图、报告、diff。
9. 回填 `docs/lightbox-method-index.md` 和模块文档。

每轮结束必须有一个能被打开、运行、截图或阅读的结果。

## 开发顺序

### R0：统一入口与开发框架

当前轮。

目标：

- 固定模块拆分。
- 建 `portfolio-site`。
- 第一屏展示工具矩阵、开发循环、证据类型。

### R1：Asset Protocol Workbench MVP

原因：

- 它是资产、LOD、材质、QC、发布的共同底座。
- 最能体现 TA 对“数据进入资产”的理解。

交付：

- asset protocol schema。
- 3 个 synthetic asset fixtures。
- 字段编辑器。
- payload preview。
- risk list。

### R2：Cross-DCC Rule Matrix MVP

原因：

- 直接体现规则工程能力。
- 能把 Maya / Blender / Max / Houdini 的差异讲成 adapter，而不是散脚本。

交付：

- rule DSL。
- adapter mock。
- collect / validate / fix / extract timeline。
- AI explanation panel。

### R3：Visual Review Studio MVP

原因：

- 作品集展示效果强，容易截图和视频化。
- 能体现固定相机/pass/report 这类真实审查经验。

交付：

- review queue。
- pass matrix。
- baseline / variant diff。
- report preview。

### R4：Texture Delivery Console MVP

原因：

- 贴图工具横跨 DCC、Photoshop、Substance、Unreal，是很好的复杂业务样例。

交付：

- preset editor。
- channel packing preview。
- queue runner。
- platform risk explanation。

### R5：Task Orchestrator MVP

原因：

- 最像真实生产平台，但依赖前面模块提供状态和证据。

交付：

- task lifecycle。
- module execution trace。
- publish readiness。
- portfolio-level case study output。

## 当前判定

先做 5 个模块，不继续扩到 8 个以上。

`LOD Bake Planner` 暂时不独立成第 6 个工具，先作为 `Asset Protocol Workbench` 的高级场景沉淀。等 R1/R2 稳定后，如果它的视觉和算法展示足够强，再拆成独立工具。

## R6 后的作品集框架

R6 增加 `Portfolio Case Study Index`，定位是全作品集证据层，不是第 6 个业务工具。

它解决三个问题：

- 面试或评审时先看到五个工具为什么要拆开。
- 每个工具都能快速对应业务场景、确定性核心、AI 边界和证据。
- 后续长期开发按 `Ready / Review / Blocked` gate 推进，而不是按 UI 完成度推进。
